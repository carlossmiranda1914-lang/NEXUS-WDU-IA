# Nexus PAP Documentation

**Status:** PAP KNOWLEDGE CAPTURE  
**Authority:** supporting academic documentation grounded in canonical repository truth.

This area exists so the student author can understand, document and present the real Nexus Edu IA project progressively.

It does **not** override product direction, architecture, Mission Packs, security/tenancy contracts, engineering evidence or implementation authority.

Before using PAP documentation, read the canonical transversal contract:

`docs/governance/NEXUS_PRODUCT_REALISM_AND_PAP_CONTRACT.md`

## Purpose

The PAP layer records:

- what problem was addressed;
- what was actually implemented;
- how frontend, API, backend and database connect;
- why important architectural decisions exist;
- what evidence proves the behavior;
- what limitations or external blockers remain;
- what the student learned and can explain to the jury.

## Truth boundary

Use only these delivery classifications:

```text
IMPLEMENTED_AND_PROVEN
IN_DEVELOPMENT
PLANNED
BLOCKED_BY_EXTERNAL_DEPENDENCY
OUTSIDE_PAP_SCOPE
```

Never describe planned or mocked behavior as implemented product capability.

## Files

- `PAP_PROJECT_SCOPE.md` — academic delivery boundary and truthful project state.
- `PAP_TECHNICAL_MAP.md` — human-readable system architecture map.
- `PAP_DATABASE_GUIDE.md` — explanation of the database/domain model.
- `PAP_DEVELOPMENT_JOURNAL.md` — concise chronological engineering/learning record.
- `PAP_PRESENTATION_GUIDE.md` — jury-facing explanation guidance.
- `feature-records/FEATURE_RECORD_TEMPLATE.md` — template for significant capabilities.

PAP documentation follows the product. It never drives weaker product engineering.
